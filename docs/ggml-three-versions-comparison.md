# 基准版、预览版与先行版对照

日期：2026 年 11 月 17 日。设备：Windows x64、i9-14900HX、RTX 5060 Laptop 8 GB，系统可见物理内存约 15.73 GiB。

用户追加要求的 [GitHub 旧 CUDA 技术分支对比](previous-cuda-comparison.md) 已另行完成，分别提供原分支 0.6B 原源码重建和相同 1.7B 路线复现，避免跨模型计算后端收益。

## 结果与选择

先行版已完工：相同的 1.7B ASR 编码和解码均可在 CUDA 上运行，原有托盘、热词与文件转录入口保持。它比预览版少 **11.24%** 完整请求耗时，但多 **722.65 MiB（22.56%）** 峰私有提交和 **154.19 MiB（7.28%）** 独显采样峰值。

三条路线没有一条同时赢得所有速度和内存指标。基准版私有提交与显存最低，预览版总工作集最低，先行版响应最快。按照本项目首先控制内存的偏好，本次保持正式 0.6.0 安装；先行版保留为已验证的性能候选。本轮没有更改自启动或推送 GitHub。

| 名称 | ASR 编码 | ASR 解码 | 模型与精度 |
| --- | --- | --- | --- |
| 基准版 | CPU ONNX Runtime | Vulkan | 现有 Qwen3-ASR 1.7B、原编码权重、Q5_K_M 解码 |
| 预览版 | GGML / Vulkan，固定 FE batch4 | Vulkan | 相同权重，编码 GGUF 按原 FP16 / FP32 精度存放 |
| 先行版 | GGML / CUDA，固定 FE batch4 | CUDA | 与预览版完全相同的编码 GGUF 和解码 GGUF |

这里统一的是 **ASR 编解码器**。Mel、文字处理和热词继续在 CPU；文件 ForcedAligner 继续使用 CPU ORT 编码与 CPU 解码。可选 0.6B ASR 编码仍使用 CPU ORT，解码由所选的 llama 后端执行。没有采用分阶段加载模型，也没有引入 ORT CUDA。

### 计时和内存口径

完整请求含 IPC、ASR，以及文件模式的 CPU 对齐和合并；输入已经是解码后的 PCM，FFmpeg 与 TXT / JSON / SRT 导出在独立实际 CLI 检查中执行。ASR 各子阶段相加没有包含整条文件链路。GGML 的诊断 `backend_run_seconds` 覆盖 FE＋BE，本表使用统一 IPC 的 `t_encode`。

保持模型加载与空闲释放策略，保留 Windows 文件缓存和驱动缓存；各进程先完成内置两秒静音的编码器预热再测首条，没有预跑完整 ASR 和文件对齐链路。ready＋首条按模型就绪加首个请求计，排除中间观测快照时间，不称为清空系统缓存后的首次安装启动。

主机目标采样间隔 25 ms，GPU 目标 100 ms。私有提交、总工作集、私有工作集、显存分别统计，不相加；进程树总工作集可能重复计算共享页，工作集降幅不等于整机物理 RAM 净降幅。末段指长文件后完成最后短句时，对齐器仍驻留的快照，不是 10 / 120 秒后的闲置占用。Job CPU 覆盖子进程完整生命周期，是多核累计 CPU 时间。

GPU 按 PID / 适配器 LUID 保存 dedicated 和 shared 原值；Vulkan 的另一个适配器真实零值保留，CUDA 缺少对应实例的读数保持 null。没有把阶段值当瞬时峰值。

上轮预览研究中基准峰提交约 2978 MiB，本轮有两次约 3160 MiB；EXE、配置、输入和结果保持相同，差异原因未证实。本页统一使用新三轮组内中位数；[上轮原报告](ggml-vulkan-encoder-research.md) 原样保留。

## 文本、时间戳与质量

### 正式性能集合

每版 15 次正式请求，共 45 次，五个结果字段及原生非计时字段全部与各自 prime、同版跨轮和其它两版匹配。文本、token 与时间戳精确一致。三版中的 GPU ASR decoder 均为 29 / 29 层；GGML 编码器 FE / BE 核心节点 CPU 回落均为零，view 等元数据节点单列。

### 八段音频、三个种子的扩展集合

每版 24 次请求；其中七段有公开参考文本，一段 60 秒切片没有逐字稿，包含重复和拼接材料，不是八段独立语料。三版有参考部分均为 **31 / 936 字符编辑，CER 3.31197%**。指标按 NFKC、大小写归一化、去标点和空白后的字符编辑距离计算。

预览对基准有 1 / 24 条原始结果变化，先行对基准 6 / 24 条、对预览 7 / 24 条；该集合中的变化为标点与英文大小写，归一化字词相同，CER 没有增减。短句的均匀分配时间戳还会随标点长度改变，最大约 226.7 ms。此小集合支持当前参考样本的质量判断，没有覆盖任意口音、噪声、专业词实录或全部录音长度。

最终配置边界修复后，预览和先行各 24 条扩展请求已重跑，与修复前各自结果全部精确一致；基准程序没有变化。

### 实际文件入口

最终程序另执行 12 次实际 CLI：三版 × 52.6 秒 / 60 秒 WAV × 两个 CLI 初始种子，每次完成 TXT、JSON、SRT，36 个文件均成功输出；与修复前各自的 36 个文件逐一字节与 SHA 相同。

跨版结果按实际差异记录：

- 52.6 秒、CLI seed 42：基准与预览相同，先行两处“现在说一下”变为“再说一下”，参考是“咱再说一下”。CER 由 8 / 208 降为 6 / 208；仍没有完整识别出“咱”。184 个共同正文 token 中，两个起点早 80 ms，其余相同。SRT 分段为 24 / 24 / 26。
- 52.6 秒、CLI seed 314159：三版三个导出文件哈希完全一致。
- 60 秒、CLI seed 42：三版三个导出文件哈希完全一致。
- 60 秒、CLI seed 314159：预览与先行三个文件哈希一致；对基准有标点、换行、`Speech` 大小写和字幕分句差异。224 个正文 token 及时间戳相同，三版均 30 段字幕。

52.6 秒有参考文件的两次 CLI 合计，基准和预览为 16 / 416（CER 3.84615%），先行为 14 / 416（CER 3.36538%）。这是两次固定样本的改善，不推断普遍识别质量更高。CLI 的 `--seed` 先经种子序列生成器，IPC 中的 `seed` 直接作为原生种子，两者相同数字不代表同一实际采样序列。

## 实现与当前产物

预览和先行使用同一个新 EXE，通过配置选择 `encoder_provider=ggml_vulkan/ggml_cuda` 与对应 `gpu_backend`；`ggml_encoder_model` 支持绝对路径或以配置文件目录为基准的相对路径。正常启动不需要研究环境变量。文件存在检查在 CLI 模型覆盖之后执行，未选中的 1.7B GGUF 不阻止切换 0.6B；选中但丢失的模型在加载原生库前明确报错。后端配置不一致明确报错，不静默切回另一模型。

398 个编码权重张量沿用正式 ONNX 数值：300 个 FP16、98 个 FP32。解码仍用原有 Q5_K_M；没有新增量化。固定每批 4 块前端、同一 scheduler 和整段后端注意力保持，编码结果仍经 CPU float buffer 传递，未实施跨图零拷贝。

CUDA 复用匹配 b9090 的原 decoder / ggml core、归档 SM120a 插件与 CUDA 12.8 系列依赖，编码 ABI 与 Vulkan 相同。保持普通 CUDA graphs，实验多流关闭。cuBLAS / Lt 保留，延迟装载只使用自有 worker PATH。详细身份、构建与导入检查见 [原生 CUDA 接入](../native/ggml-cuda-encoder.md)。这些本机二进制针对 RTX 5060 Laptop，其它 GPU 需对应架构构建。

## 复现入口

先按 [上轮同权重转换与 batch4 说明](ggml-vulkan-encoder-research.md) 准备原生编码 DLL、等值 GGUF 与固定 PCM；使用 [CUDA stage 工具](../tools/research/stage_ggml_cuda_native.py) 准备匹配的 CUDA-only 原生目录。

在固定源码版本的新 detached worktree 运行 [候选接入工具](../tools/research/stage_ggml_encoder_candidate.py)，然后在该树正常执行 `build.ps1 -Tests` 和 `build.ps1`。接入工具校验原编码器源码 SHA 并拒绝覆盖已接入的文件。

[三版测量工具](../tools/research/bench_ggml_three_routes.py) 的 `prepare / stage / plan` 分别准备输入、复制候选资产、生成串行三轮命令，不加载模型；`run` 才执行指定候选。每次使用新输出目录；[汇总工具](../tools/research/summarize_ggml_three_routes.py) 生成带逐轮范围和身份信息的 JSON / 文本。[质量工具](../tools/research/quality_ggml_routes.py) 的 `prepare / analyze / exports / cli-run` 处理公开逐字稿、多种子及实际导出，其中 `cli-run --execute` 才运行文件转录。
