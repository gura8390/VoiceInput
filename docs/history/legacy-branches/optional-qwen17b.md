# 可选大模型配置分支归档

归档对象：`feat/optional-qwen17b`，分支头为 **`a959261f27fa71d9437d8695ae7c100979f2c35a`**（0.4.5，原报告日期 2026-10-27）。2026-11-18 只读核实，该提交已是 `main` 的祖先。删除已合并分支名不会删除这项能力或它的提交历史。本文保存当时的实现、测量及没有开展的内容，不把旧数据重新标为 0.6.0 或 GGML 数据。

## 增加的能力

这次改动把 ASR 模型从单一固定配置扩为两个明确档位，继续使用同一 Rust 应用、CPU ONNX Runtime 编码和 Vulkan 解码路线，保留实时听写、热词与文件转录。

- 配置新增 `asr_model`，仅接受 `0.6b`、`1.7b`。当时默认仍为 `0.6b`，旧配置缺字段也保持小模型。
- 新增全局 `--asr-model` 参数，可为桌面、服务或文件转录覆盖本次模型选择，覆盖不写回配置。
- 引擎按型号选择目录、编码器及解码器文件，使用模型自身的嵌入维度。选中模型文件缺失时明确报错，不静默换成另一个型号。
- 模型选项从配置传到实际推理引擎；文件 ForcedAligner 仍使用原独立 0.6B，热词、格式化和其余参数不随 ASR 型号更换。
- 增加同机双模型测量工具、事务部署策略与相应测试。旧部署策略只加入原 1.7B 三件资产及两个档位快捷方式，保护既有原生库和用户数据；它针对当时的旧目录布局，属于历史实现说明。

模型切换是退出当前实例后重新启动，不是运行中热切换，也没有让两个模型同时常驻。后续正式配置已选 1.7B，0.6B 仍可选；这与本分支最初“默认 0.6B、新增可选 1.7B”的时间顺序分开记录。

实现来源均固定到原提交：[模型枚举与文件映射](https://github.com/gura8390/YuYbUuRu/blob/a959261f27fa71d9437d8695ae7c100979f2c35a/src/config.rs#L5-L42)、[CLI 覆盖](https://github.com/gura8390/YuYbUuRu/blob/a959261f27fa71d9437d8695ae7c100979f2c35a/src/main.rs#L19-L79)、[模型缺失预检](https://github.com/gura8390/YuYbUuRu/blob/a959261f27fa71d9437d8695ae7c100979f2c35a/src/engine.rs#L167-L179)、[配置传递](https://github.com/gura8390/YuYbUuRu/blob/a959261f27fa71d9437d8695ae7c100979f2c35a/src/pipeline.rs#L19-L40)。

## 权重格式与识别质量分开

| 档位 | 编码权重 | 解码权重 | 当时定位 |
| --- | --- | --- | --- |
| 0.6B | 原 INT4 ONNX，FP32 激活 | 原 Q4_K GGUF | 更低资源、更短响应的默认档 |
| 1.7B | 项目先前保留的原 FP16 ONNX 资产 | 原 Q5_K_M GGUF | 保留原大模型资产的可选档 |

这里的 FP16、INT4、Q4_K、Q5_K_M 描述数值格式，不是识别准确率。1.7B 编码器在 CPU 执行时仍可能发生 FP32 转换和预打包；“保留 FP16 资产”不等于所有 CPU 运算或内存缓冲均为 FP16。Q5_K_M 解码器本来已经量化，“原大模型”也不代表全链路无量化。

本次比较同时改变模型参数规模、编码权重格式和解码量化，不能把所有资源或速度差距单独归因于参数量。没有人工标注 CER/WER 数据，归档结论不宣称 1.7B 普遍更准，也不宣称 0.6B 与 1.7B 识别质量相同。

## 旧版本的资源与时间取舍

两档使用同一个最终 0.4.5 EXE，SHA256 为 `f5330bd7088c02d5a4a04d724960c7a210062c809bba6a1bf25acdff27361b80`。相同机器、输入、种子和其余设置；每种模式先各留一个预热过程，再按 AB / BA / AB 交错三轮，以下为正式轮中位数。听写每轮 39 请求、共 551.25 秒输入；文件每轮是七个独立完整 PCM 请求、共 253.25 秒输入。

| 指标 | 0.6B INT4 / Q4_K | 1.7B FP16 / Q5_K_M | 1.7B 相对 0.6B |
| --- | ---: | ---: | ---: |
| 39 次听写累计完整请求，秒 | 15.8575 | 34.4841 | +117.46% |
| 听写观测峰值私有提交，MiB | 1243.52 | 3695.43 | +197.18% |
| 听写观测峰值总工作集，MiB | 721.71 | 2863.63 | +296.79% |
| 听写阶段最大专用显存，MiB | 647.60 | 1492.53 | +130.47% |
| 七次文件累计完整请求，秒 | 20.1157 | 27.3466 | +35.95% |
| 文件观测峰值私有提交，MiB | 1779.68 | 4071.21 | +128.76% |
| 文件观测峰值总工作集，MiB | 1219.66 | 2685.69 | +120.20% |

这套固定负载下，小模型的资源和耗时优势明确；新增大模型是给用户保留选择，不是宣称它更省内存或更快。

内存按约 25 毫秒采样自有 service / worker 进程树，排除桌面进程和全系统其它程序。私有提交、工作集及显存是不同指标；采样峰值是观察到的峰值，GPU 这里只是阶段快照，不是瞬时显存峰值。完整请求累计时间不含模型预热，文件首请求可能包含对齐器首次加载。新进程保留 Windows 和驱动缓存，不是重启后的冷盘测试；七条独立 PCM 请求也不是一份多段媒体的整段转录时间。

两档产生的 token 数不同，且重试时 `t_generate` 可能只保留最后一次生成，因此本表使用完整请求时间，不把生成子阶段耗时当作完整响应。

## 117 / 21 是各自参考回归

每模型的正式三轮共有 **117 次听写（39 × 3）和 21 次文件请求（7 × 3）**。两档最终无中止、无空文本，并对各自固定参考逐项一致：

- 0.6B 使用原 0.4.4 的小模型参考，证明加入可选型号后，既有小模型路径保持原输出。
- 1.7B 第一轮预热先与小模型比较，随后把自己的预热输出作为固定参考，三轮正式请求均与自己的参考一致。
- 比对包括五个结果字段 `duration / text / text_accu / tokens / timestamps` 和五个原始字段 `text / token_ids / n_prefill / n_generate / is_aborted`。它不是只比一句整理后的文字，也不是“117 / 117 识别正确”。

跨模型预热比较中，39 次听写有 **25 条最终结果字段不同、26 条原始字段不同**；七次文件有 **6 条最终及原始字段不同**。这些计数包含文字、token、格式及时间戳差异，不是错误条数。没有逐字稿评分，就不把“不同”转换成准确率升降。

额外旧记录确认两档各六份实际媒体 TXT / JSON / SRT 导出与对应沙盒哈希一致，命令行覆盖及 worker 空闲释放／重载路径通过；生命周期检查使用缩短的超时，生产 120 秒 ASR、10 秒对齐器设置保持原样。本轮未重新测试物理热键。它们与上述 117 / 21 的服务请求回归是不同检查项。

## 为什么保留原 1.7B 编码精度

本分支的任务是把先前那套大模型重新接入测试并做成可选配置，因此直接复用已保留资产，三文件按名称、大小和 SHA256 绑定。这样得到的是“原 1.7B 档位”的资源和输出记录，而不是在接入时同时再改变编码量化。

| 原 1.7B 文件 | 字节数 | SHA256 |
| --- | ---: | --- |
| `qwen3_asr_encoder_frontend.onnx` | 24,063,978 | `fc288ba9a0ca732251b33628c803cd5188d3dd77a2cd7336f0f0fd37969ed4cd` |
| `qwen3_asr_encoder_backend.onnx` | 611,276,553 | `4b0b1e34e8393f29222006aae0719283b0ff28b61f289b6ff8377b3ddbda27e3` |
| `qwen3_asr_llm.gguf` | 1,471,800,896 | `89e198470f41d487ab5b6b8a36a35400b3b1534451c4499236983050fe9193e5` |

合计 **2,107,141,427 字节**，这是文件逻辑大小，不是运行内存。原提交的 [部署资产约束](https://github.com/gura8390/YuYbUuRu/blob/a959261f27fa71d9437d8695ae7c100979f2c35a/tools/deploy_asr_models.py#L14-L24) 明确只接受这些原始文件。

**没有发现本分支进行新的 1.7B INT4 编码器校准、其它解码量化筛选或带人工真值的额外量化质量实验。** 因此应记为“本次保留原精度、没有开展额外量化”，不能写成“测过所有量化方案后证明原 FP16 最优”，也不能编造量化导致识别下降的数据。额外量化若今后另做，需要独立的模型身份、质量与资源对照。

本分支增加的是已采用并进入主线的模型选择能力，没有独立的失败量化方案可归档。README 中继承的 CPU 调度、CUDA graph 等研究属于其它分支的既有背景，应放在各自研究归档中。
