# GGML / Vulkan 统一编解码器研究

日期：2026 年 11 月 17 日。对照版本：正式 0.6.0，默认 Qwen3-ASR 1.7B。

## 结论与当前状态

统一 ASR 编码器和解码器的 GGML/Vulkan 路线已经跑通，并完成隔离原型、同权重转换、两组各三对进程的测量及实际文件入口检查。最终研究候选采用固定 4 块前端批次，保留原有整段后端注意力。

本机第二组对照中，五请求累计编码耗时降低 **92.70%**，完整请求合计降低 **33.78%**；采样峰总工作集降低 **56.35%**。代价为峰私有提交增加 **7.57%**、混合请求末段私有提交增加 **33.25%**、独立显存峰增加 **48.03%**。

这条路线具有明确的速度收益，但没有在全部内存指标上胜出现有版本。按本项目优先控制内存的要求，本轮保留它作为性能候选，正式安装继续使用 0.6.0 的 CPU ORT 编码器＋Vulkan 解码器。没有改自启动、正式配置、热词、正式模型或正式运行库，没有发布新版本。分阶段加载模型没有实施。

## 接入方式

现有 Rust 托盘、实时听写、热词和文件转录入口保持；原型只在分离的研究工作树替换 1.7B ASR 编码计算。可选 0.6B 与文件 ForcedAligner 沿用原 ORT 实现。因此统一的是 ASR 编解码技术栈，整个应用仍有文件对齐器的 ORT 依赖。

流程为：原 Rust Mel 提取 → 同样的 FP16 输入边界 → GGML/Vulkan 分块卷积与位置编码 → FP16 前后端边界 → 整段 GGML/Vulkan 双向注意力与投影 → FP16 输出边界 → 原有 Q5_K_M Vulkan 解码器。Mel、文字处理、热词等 CPU 工作继续保留。

原生库采用匹配 b9090 / `5757c4dcb178a01c85234a6db7503b19c9598873` 的窄 C ABI，新增研究用 `caps_encoder.dll`，保留正式 `llama.dll`、ggml 及 Vulkan 后端的实际二进制。正式解码器的单输出、有界上传等优化保持。

上游旧 Qwen3A 图没有正确处理 100 帧卷积分块和逐块位置重置；研究回移了 [72e60f5 修复](https://github.com/ggml-org/llama.cpp/commit/72e60f500d739eb9dc26e51cda5fdfe062faf766)。没有接入其按 800 mel 帧切窗的 PCM 入口，因为它会改变现有的整段后端注意力。编码结果仍读回 CPU float buffer 再交给原 decoder，没有实施跨图零拷贝。

首版方案、ABI 与复现说明见 [原生接入记录](../native/ggml-vulkan-encoder.md)，最终前端批次优化见 [固定批次记录](../native/ggml-vulkan-encoder-batched.md)。构建 caps 所用源码底座包含 aligner/single-output 补丁；有界上传由原样复用的正式 decoder DLL 提供，没有用新构建的 llama DLL 覆盖它。

## 权重身份

保持当前 1.7B 解码 GGUF，不采用官方整套 Q8 解码器。官方 [BF16 mmproj](https://huggingface.co/ggml-org/Qwen3-ASR-1.7B-GGUF/tree/36a678687ba7d07a74ca70ccb0e36902e005fb80) 只作 GGUF 名称、布局及元数据模板。

实际编码权重全部来自正式 ONNX：398 个权重张量，300 FP16、98 FP32；按映射后的布局读回 dtype 与 payload SHA 全部一致。另 6 个 initializer 是形状、轴、头数和缩放常量，记录在本机转换收据中。位置表保留原前端实际使用的 13 行，没有新增量化。

模板直接转 FP16 与正式权重有 1,453 个极小值不同，最大差 `1.1920928955078125e-7`。派生文件直接使用正式值，避免把历史 FP16 转换差异混入后端比较。

## 测量口径

环境：Windows x64、i9-14900HX、RTX 5060 Laptop，系统可见物理内存约 15.73 GiB。保持 CPU ORT 8/1 线程、原 decoder、采样参数、热词、文件对齐及模型闲置策略。

每轮 5 个请求，4 段不同 PCM：公开中文短句、中文问候、英文短句、精确 60 秒混合音频，最后重复第一条短句。60 秒音频从已有公开混合 WAV 固定截取前 960,000 帧，16 kHz 单声道，记录 WAV 与 float32 PCM SHA。

两组分别比较首版全批次与最终固定 4 块方案；每端各 3 个新进程，顺序均为基线、候选、候选、基线、基线、候选。保留 Windows 文件及驱动缓存。先预热，再记录第一条完整请求；它不是未预热的首句。另列启动至 ready 及 ready＋首句。

正式统计不含 profile 或 embedding 文件写入。主机内存目标采样间隔 25 ms，GPU 目标 100 ms；按自有 service/worker Job 树统计。以下峰值是观测采样峰，末段是完成长文件后再完成短句时的快照，含仍驻留的对齐器，不称作长时闲置占用。ready 工作集受两端相同的加载后 trim 策略影响，不用它估计日常使用内存。

完整请求时间包括 IPC、识别及文件模式下的对齐/合并；输入 PCM 已解码，不包括读取媒体、FFmpeg 解码和 TXT/JSON/SRT 落盘。实际文件入口另测。显存按 worker PID 与适配器分别记录，不与主机提交相加；另一个适配器的真实零值保留。每组 12 张前后后台快照均只记录到原正常托盘进程，没有正式模型 worker；这些快照覆盖各轮开始和结束。

## 进一步压低 GGML 缓冲

首版将所有 100 帧块一起卷积，长输入产生数百 MiB 的 im2col 与激活；ggml allocator 在较小图到来时不自动缩容，长文件后的高水位被保留。

最终方案保持同一个编码模型、GPU 权重、后端及 scheduler，只把前端计算固定为每批 4 块，汇总 FP16 边界后的 hidden，再一次执行原整段后端注意力。没有卸载或交替加载模型，没有拆分后端注意力。

60 秒诊断中执行 15 次 FE，每次 27 个计算节点，以及一次 778 个计算节点的 BE，计算节点全部分配到 Vulkan；CPU view 等元数据节点单列。共享 GPU 计算池为 77,440,000 字节，约 73.85 MiB；CPU 计算池约 3.05 MiB。Mel 等图外 CPU 工作另算。

两组候选的采样峰私有提交中位数由首版 4239.05 MiB 降到固定批次的 3203.56 MiB，相差约 1035.49 MiB；独立显存峰由 3157.66 降到 2119.32 MiB。这是两个组内候选的观察，不把跨组速度差重新包装成新的配对性能百分比。

每批 1 块另作一轮筛选，只再少约 36 MiB 峰私有提交，却改变了 60 秒样例的文字、token 和时间戳，已拒绝。固定 4 块方案与首版的 5 组完整 float32 embedding **逐值精确相同**。

## 输出与质量检查

两组正式轮分别有 15 对请求，duration/text/text_accu/tokens/timestamps 及原生 text/token_ids/n_prefill/n_generate/is_aborted 全部精确一致。三个有公开逐字稿的短句，双方归一化字符错误率均为 0；60 秒混合切片没有逐字稿，只做输出回归。

GGML 与 ORT 编码浮点输出不逐位相同：这 5 组诊断最小余弦相似度约 0.999906，最大单元素绝对差约 0.01907。权重字节一致不等于推理运算逐位相同，不能用单纯的余弦相似度证明识别率。

实际 CLI 使用同一 60 秒 WAV 和另一组固定采样种子 314159，各执行两次。两端均成功输出 TXT/JSON/SRT，且各自两次的三个文件全部精确复现；两条路线之间三个导出文件的 hash 不同。差异是标点、大小写和字幕分句。移除标点/空白并折叠大小写后，正文 token 序列一致，224 个对应正文 token 的时间戳也全部相同，最大差 0 秒。原始导出差异仍按差异保留，不算作三文件精确通过。

本轮没有对 CapsWriter、Godot 等个人术语实录或大规模人工标注语料做识别率评测，也没有在其他显卡与驱动上测量。

## 剩余空间与部署判断

最终候选尾段仍多约 730 MiB 私有提交，同时独显峰多约 688 MiB。源码没有保留整份 CPU 编码权重副本；加载临时 read buffer 在加载后销毁。差额与 GPU 编码器权重、计算池和驱动资源同量级，这是机制推断，没有把驱动提交精确拆账为已证实比例。

简单把 loader 改 mmap 不能直接消除此差额。当前后端没有开放稳定的文件映射 GPU buffer 入口；流式权重或 host-pointer 导入会增加复杂度和 PCIe 传输成本。剩余低成本 scratch/metadata 调整主要是几 MiB 至十几 MiB，不继续扩展本轮。

研究原型已完成。它适合作为减少等待、降低进程驻留工作集的候选；当前省提交量路线继续保留。正式安装没有切换，研究源码、失败记录和复现工具均保留。
