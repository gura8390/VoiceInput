## 已采用方案的测量

### Python 精简与 Rust 重构

Python 三功能精简阶段，同一运行库的单模型对照在 30 段识别后，原 1.7B 与当轮 0.6B 的私有提交分别约为 2069.8 和 1371.6 MiB，总工作集约为 2649.9 和 741.1 MiB。模型、精度和运行方式均发生变化，后续质量结论需要分别核验。该轮还移出 38 项可选运行包，共 161,298,018 字节。

### 冷启动与文件内存

0.4.3 最终文件方案在各三轮、每轮七个独立 PCM 请求的对照中，峰值私有提交约从 3047.8 降至 2006.1 MiB，减少 34.18%，末短请求检查点的私有提交约从 2813.7 降至 1406.0 MiB，累计请求时间约从 21.067 降至 20.995 秒。

## 已停止的性能路线

### CUDA

CUDA 未优化基线与采用单输出预留及 cuBLAS 延迟加载后的私有提交采样峰值分别为 1940.51 和 1431.93 MiB，减少 26.21%。固定 token 解码回放的热态吞吐为 CUDA 324.57、Vulkan 279.80 token/s。

在两条路线都启用单输出预留的完整请求对照中，CUDA / Vulkan 的私有提交采样峰值分别为 1431.93 / 1209.85 MiB，39 请求累计耗时为 17.789 / 17.433 秒，专用显存阶段读数为 749.48 / 647.60 MiB。完整请求的比较支持继续采用 Vulkan。实验性的多流 CUDA Graph 还出现过一次内核启动失败。

源码分支、原生补丁及精简报告已保留。2026 年 11 月 6 日归档源码和关键测量证据后，清理了九个本地构建或实验目录，共 7785 个文件及 39 个目录联接。共享依赖和原始记录分开核验。[CUDA 技术路线归档](https://github.com/gura8390/YuYbUuRu/blob/b96d7840c26b8b3da82e34ad4ec7adaeadccdc52/docs/benchmarks/cuda-route-archive.md)

### CPU 与 Vulkan 调度

## 维护与验收口径

主机工作集、私有工作集、私有提交量和专用显存分别统计。采样峰值受间隔限制，各阶段快照只描述对应时间点。独立请求累计、冷启动、真实媒体导出和桌面交互分别验收。百分比按各轮匹配基线计算，各阶段收益不累加成统一的降幅。

固定输入的文本、token、时间戳和浮点输出回归用于控制实现变化。模型切换或新模型的普遍识别质量仍需要更充分的人工参考。历史文档与原始证据用于复查已经做过的路线，后续实验应先核对本记录中的结论、版本及验证范围。

1.0.0 候选版本保留托盘操作方式，整合为单一中文启动入口，补齐嵌入图标、DPI 感知、登录启动和面向自动化的接口。最终行为和通过项由该候选的验收记录说明，本历史表沿用已完成的测量结果。

## 1.0.0 加载瞬时工作集

2026 年 11 月 16 日的目录整理对照中，旧版也出现过高加载峰值；新版中位数偏高的原因没有完全确定。随后通过阶段时间戳和内存记录，确认 GPU 模型读取与编码器首次预热的驻留叠加是主要峰源。不能据此宣称目录改动新增加了等量常驻分配。

直接关闭整个 GPU ASR 模型的 mmap 虽降低工作集，却增加约 208 MiB 常驻私有提交；编码器先加载会增加约 23% 初始化耗时，这两项未采用。最终仅改变 Windows Vulkan GPU tensor 的上传方式，复用已有有界异步环；CPU embedding 仍映射，CPU 文件对齐器和 CUDA 路径保持原策略。没有更换权重、量化或推理计算，没有关闭预热或内存整理来转移测量阶段。原生补丁和复现方法位于源码的 `native/windows-vulkan-bounded-upload.md`。

最终载荷与目录整理后原 1.0.0 比较，固定 1.7B、CPU 8/1 线程、Vulkan、公开样例及 seed。每版五轮新进程加载的单 worker 内核工作集高水位中位数为 2434.33→2074.17 MiB，减少 360.16 MiB（14.80%）；各轮观测范围为 2309.68–3616.03 和 1926.44–2593.94 MiB。加载后私有提交增加约 7.30 MiB，工作集约 22 MiB。初始化请求中位数为 1.516→1.343 秒，真实首条识别为 1.930→1.944 秒。

每版三轮混合请求中，峰值私有提交中位数为 3832.01→3596.67 MiB，减少 6.14%；独立完整长文件转录为 7.294→7.364 秒，增加 0.95%。完整 CLI 的采样工作集峰值中位数反而增加约 14.38%，累计 CPU 时间中位数也偏高且范围较宽，因此本次结论限定为加载阶段和上述测量，不能宣称所有阶段的内存或 CPU 都下降。冷进程保留 Windows/驱动缓存，工作集不等于整机物理 RAM，也不与私有提交相加。

36 条正式混合请求以及两端预热的文本、token、时间戳和原生指标一致；六次完整转录的 18 个导出文件哈希一致。0.6B 另做公开短音频的 TXT/JSON/SRT 对照，三项哈希一致。模型权重、配置和其他运行库保持原样；最终 EXE 与 DLL 的本地收据及逐轮数据保存在本机 `evidence/transient-ws-20261116/`，不作为公开源码载荷。

## 1.0.1 持续内存优化

2026 年 11 月 16–17 日，在默认 1.7B、CPU8/1＋Vulkan 和当前模型精度下，采用三套编码 ONNX 的等值外置权重、ASR 动态上下文、忙队列中的独立对齐器闲置释放，并补齐模型配套文件预检与文件加载失败的及时反馈。

最终载荷与本轮起点 1.0.0 各三轮匹配测量：混合峰私有提交 3835.67→3215.84 MiB（减少 16.16%）；末段私有提交 3133.70→2364.10 MiB（减少 24.56%）；真实 CLI 峰私有提交 3543.66→2596.32 MiB（减少 26.73%）；CLI 单 worker 内核工作集峰 2099.28→1931.48 MiB（减少 7.99%）。稳态工作集基本相同；部分请求存在几十至数百毫秒代价，冷首句也有不利轮次，具体范围和逐阶段结果保留在报告。

CPU noRepack 初筛减少约 205 MiB，但完整文件 JSON 中一个时间戳改变 80 ms，已归因并撤回。ORT1.32、All99 离线缓存、固定对齐器线程及 Vulkan host-visible 开关均未形成合适的整体收益。保持原 CPU repack、ORT1.24、线程和 Vulkan 路线。严格回归覆盖两型号、完整 float32 编码、52.6／157.8 秒媒体导出和实际 10／120 秒生命周期。详见 [持续内存优化报告](memory-optimization.md)。

## 0.6.0 后续：GGML/Vulkan 统一编解码器研究

2026 年 11 月 17 日，使用正式 1.7B 的相同权重与原 Q5_K_M decoder，在隔离工作树接入 GGML/Vulkan 音频编码器。398 个编码权重张量按正式 FP16/FP32 dtype 和字节等值转换。保留现有 mel、100 帧前端分块、整段后端注意力与文件对齐器；没有实施分阶段加载模型。

首版全前端批次造成大工作区高水位。固定每批 4 块、复用同一 scheduler 后，5 组编码输出对首版逐 float 相同，候选峰私有提交中位数从约 4239 降到 3204 MiB。最终与当前 0.6.0 各三轮交错对照：累计编码耗时减少 92.70%，五请求合计减少 33.78%，峰总工作集减少 56.35%；同时峰私有提交增加 7.57%、混合末段私有提交增加 33.25%、独立显存峰增加 48.03%。这些是新固定五请求工作负载，不与早期 39 请求的 9.33 秒直接换算。

固定请求的 15 对结果精确一致。实际 CLI 另一固定种子两次对照存在标点、大小写、字幕分句差异；归一化后的 224 个正文 token 与对应时间戳相同，各路线自身重复可精确复现。每批 1 块只额外省约 36 MiB，却改变长样例输出，未采用。研究原型与补丁保留，正式 0.6.0 安装保持原 CPU ORT 编码＋Vulkan 解码。完整方法、取舍与证据见 [统一编解码器研究报告](ggml-vulkan-encoder-research.md)。
